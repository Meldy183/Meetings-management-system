**План реализации формата участия «Очно / ВКС»**

Статус: реализация завершена, независимое код-ревью и локальная проверка завершены. Дата: 8 октября 2026 года. Каждый шаг ниже — отдельная проверяемая единица изменения. При изменении интерфейсов адаптация вызовов, фикстур и сгенерированных моков входит в тот же шаг, чтобы проект оставался собираемым. «Атомарный шаг» означает законченное проверяемое изменение; существующий мастер создаёт встречу несколькими HTTP-запросами и не становится одной транзакцией в рамках этой задачи.

**Согласованный результат.**

Формат участия задаётся для человека в конкретной встрече. По умолчанию — «Очно», включая участников существующих встреч. Докладчик является участником этой встречи и получает формат из той же записи. Председатель исключается из таблиц участников. Один DOCX «Список участников» содержит сначала группу «Очно», затем «ВКС»: каждая непустая группа имеет свой заголовок и таблицу с нумерацией с 1. Пустая группа не выводится целиком, включая заголовок. Внутри групп сохраняется текущий порядок участников.

Трактовка пункта 1 для ревью: докладчик попадает в соответствующую таблицу списка участников на общих основаниях. Отдельный формат участия для назначения докладчиком не создаётся. Изменение документа в этом плане относится к DOCX «Список участников»; отдельная пометка «ВКС» в DOCX «Повестка» не следует однозначно из ответа и в объём реализации не включена.

**Технический контракт.**

Поле `attendance_mode`: `in_person` → «Очно», `vcs` → «ВКС». Источник данных — `meeting_participants`, ключ `(meeting_id, person_id)`. Глобальные сведения человека и Excel-импорт продолжают описывать самого человека; формат выбирается при включении во встречу.

Участник встречи возвращается с текущими полями человека и дополнительным обязательным `attendance_mode`. Формат докладчика определяется по его `person_id` в составе встречи. Отдельной копии этого значения в назначениях докладчиков нет.

| Операция | Контракт |
|---|---|
| `POST /meetings/{id}/people` | `{ "person_id": 42, "attendance_mode": "vcs" }`; при отсутствии поля формат — `in_person`. |
| `PATCH /meetings/{id}/people/{pid}` | `{ "attendance_mode": "in_person" }`; изменяет формат уже добавленного участника. |
| `GET /meetings/{id}` | Каждый элемент `people` содержит `attendance_mode`. |
| `GET /meetings/{id}/people` | Каждый элемент ответа содержит `attendance_mode`. |
| Успешные POST/PATCH | `200` и актуальный полный объект встречи. |
| Некорректный формат | `400`: пустое значение, `null`, неизвестное значение; в PATCH также отсутствие поля. |
| Некорректный `pid` в PATCH | `400`: не целое положительное число. |
| PATCH для отсутствующей связи | `404`, включая отсутствующую встречу или человека, который в неё не добавлен. |

Старый POST только с `person_id` продолжает работать. Изменение формата допускается для председателя и докладчика, сохраняет их назначения и не меняет позицию в списке. Успешное повторное назначение того же формата возвращает текущую встречу. PATCH использует ту же авторизацию, что остальные операции встречи; без действующей сессии или API-ключа — `401`.

В HTTP-запросах optional-поле разбирается через `json.RawMessage`: отсутствующее значение отличается от явных `null` и `""`. Shared-функция разбора допускает отсутствие только для POST, принимает ровно две указанные строки и отклоняет остальные типы JSON. Default назначается до передачи конкретного доменного значения в сервис. В консоли сохраняется такое же различение, чтобы ошибочное значение не превращалось в «Очно».

Проверки DOCX разбирают `word/document.xml` через XML-парсер и проверяют таблицы и их строки: число таблиц, соответствие участников группам, независимые номера, относительный порядок, отсутствие председателя внутри таблиц и отсутствие пустых заголовков. Поиск фамилии по всему XML не подтверждает исключение председателя, потому что его имя законно присутствует в шапке. Визуальная проверка охватывает смешанный состав, одну непустую группу и многостраничный список; также проверяется, что заголовок группы не остаётся один внизу страницы.

**Подготовка тестовой БД и проверка миграции.**

Использовать отдельный Compose-project `meetings-attendance-test`; одинаковый `-p` обязателен для всех команд этой проверки. Запускать только нужные сервисы, чтобы не занимать порт пользовательского frontend. Сначала выполнить из корня репозитория:

```bash
docker compose -p meetings-attendance-test --profile test up -d --wait db
docker compose -p meetings-attendance-test exec -T db psql -U meetings -d postgres -Atc "SELECT datname FROM pg_database WHERE datname = 'meetings_editor_test'"
```

Если проверка вернула пустой результат, явно создать `meetings_editor_test` через `createdb -U meetings` внутри этого контейнера. На init-скрипт нельзя рассчитывать при повторном использовании volume: он выполняется только при первой инициализации PostgreSQL. DSN для миграций внутри Compose-сети: `postgres://meetings:meetings@db:5432/meetings_editor_test?sslmode=disable`.

Для baseline применить текущие миграции командой `docker compose -p meetings-attendance-test --profile test run --rm --no-deps migrate-test`. Для отдельной проверки 009 сначала привести эту тестовую БД к версии 008 той же командой с аргументами `-path=/migrations -database=<test-dsn> goto 8`, создать фикстуру старой встречи с участниками и фиксированными позициями, затем применить `up`. Проверить default для существующих и новых связей, CHECK через недопустимое значение и допустимые `in_person`/`vcs`; scoped update проверяется после шага 6. Выполнить `down 1`, проверить сохранение встреч/людей/позиций и удаление колонки, затем `up`; после повторного up режимы восстанавливаются как `in_person`, поскольку down намеренно удаляет данные колонки. Оставить БД на актуальной версии перед suite.

Пересобрать образ тестов и выполнить suite с прямым кодом завершения Go:

```bash
docker compose -p meetings-attendance-test --profile test build run-tests
docker compose -p meetings-attendance-test --profile test run --rm --no-deps run-tests go test -p 1 -count=1 ./...
```

В текущем Compose порт `db` не опубликован на host, поэтому эта процедура запускает интеграционные тесты внутри `run-tests`, где `TEST_DATABASE_URL` уже задан для `meetings_editor_test`. Локальный запуск допустим только с отдельно подготовленной доступной тестовой БД и явно заданным `TEST_DATABASE_URL`; не допускать fallback на рабочий `DATABASE_URL`. Repository-тесты очищают таблицы, поэтому адрес рабочей БД для них недопустим. Текущий `tests.sh` здесь не используется: он удаляет Compose-volume с базой и выполняет глобальную очистку Docker-сетей.
